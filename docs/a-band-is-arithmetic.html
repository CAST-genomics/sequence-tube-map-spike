Sequence tube map · rendering tech note · 19 August 2026

A Band Is
Arithmetic

The renderer draws 40,442 curved bands in one draw call and holds 8.3 ms a frame from fit-to-width to 200× zoom. It does it by never storing a vertex, never tessellating a curve on the CPU, and never touching geometry when anything changes. Every band in the document is six floats; every pixel's edge quality is solved, not sampled; and the answer to “which haplotype is under the cursor” comes from the same arithmetic that put the ink there.

Vocabulary

Two vocabularies meet in this document — pangenomics and real-time graphics — and the interesting part is where they touch. Neither is assumed below.

Legend
haplotype / strand
One individual's one copy of a genomic region, drawn as a single continuous ribbon crossing the map. A document holds 369–466 of them. “Strand” is this renderer's word for it.
band
One drawn piece of one strand: the segment between two graph nodes. A strand is 13 to 47 bands; a document is up to 40,442 of them. The unit of rendering.
tube map
The picture: hundreds of strands running left to right in parallel bundles, weaving vertically where the graph branches and rejoins. Delivered by the server as an SVG document — which is the input this renderer reads and then declines to use as a rendering medium.
instanced draw
The GPU draws one mesh N times in a single command, giving each copy its own slice of per-instance data. One command, 40,442 bands.
vertex / fragment shader
The two programs in the pipeline. The vertex shader decides where things are; the fragment shader decides what colour each covered pixel gets. Both run massively in parallel.
varying
A value the vertex shader computes and the rasterizer interpolates across the triangle before handing it to the fragment shader. flat suppresses the interpolation and hands over one value per primitive.
coverage
What fraction of a pixel a shape actually fills. The number antialiasing is trying to estimate — and the number this renderer computes exactly.
MSAA
Multisample antialiasing: the hardware's estimate of coverage, taken by testing 2–8 fixed points inside each pixel. Four samples can only ever answer in quarters.
conflation artifact
The error you get when two shapes that exactly abut are each composited independently against the background — the seam leaks background through. Classic in SVG; inherited here, on purpose.
PCLAI colour
The upstream ancestry encoding that assigns each strand its colour. The renderer reads this field and is never permitted to alter it. A fixed constraint, not a style choice.
§

The wall this was built against

The shipping viewer draws the tube map as SVG. On 5520+ that is a 14.2 MB document and 40,442 DOM elements, and it fails in three separate ways at once: zooming re-rasterizes a layer that reaches 900 megapixels, changing the appearance of the strand under the cursor costs ~28 ms of style invalidation across ~10,000 elements — 190 of 582 frames dropped during a single sweep — and the viewer's zoom ceiling of 4× never resolves a single haplotype on the documents that matter.

None of those are bugs. They are the cost of the model: one retained object per drawn thing, with the browser responsible for keeping all of them consistent. The renderer described here changes the model. Nothing is retained per band except six numbers, and no CPU work is proportional to the band count after load.

01

A band is six floats

The whole design rests on one empirical fact, established by surveying every band in every document the API returns: 127,101 of 127,101 band paths match a single grammar.

The grammar · every band, every document 
M x0 y0  C cx y0  cx y1  x1 y1   V y1+15  C dx y1+15  dx y0+15  x0 y0+15  Z

Read it as: go out along a cubic whose two control points share the abscissa cx and whose control ordinates are copies of the endpoints; drop 15 units; come back along a second cubic with its own shared abscissa dx.

That degeneracy is worth dwelling on, because it is what makes everything downstream cheap. A general cubic needs eight numbers per edge and a root-find to evaluate at a given x. This one collapses. Normalise by the span, write u for the control abscissa as a fraction of the width, and the two coordinate functions separate completely:

The band, as two functions of one parameter 
x(t) = 3u·t·(1−t) + t³        // normalised to the span: x0 + width·x(t)
y(t) = y0 + (y1−y0)·(3t² − 2t³)   // literally smoothstep

y is smoothstep because the control ordinates are copies of the endpoints — there is no Bézier evaluation in y anywhere in this renderer, in either shader.

And one identity carries the rest of the document:

The load-bearing identity

x(0) = 0 and x(1) = 1 for every u. The two edges of a band therefore meet at both ends however much their control abscissae differ — so the top and bottom edges can be sampled at the same parameter t and still close into a watertight polygon with vertical ends. No seam, no root-finding, no shared x.

Where this comes from. parseBands.ts reads the response text with a regex, never DOMParser — building 40,442 DOM nodes is exactly the cost being escaped. It also flips y, centres the map on the origin, and refuses the whole document if a single band does not match. A half-drawn map looks like a correct map of different data.

02

The ladder: a mesh with no positions

There is exactly one mesh in the scene. It is a strip of 64 quads spanning the curve parameter from 0 to 1, two rows deep, and it carries no positions at all — only, per vertex, a parameter t and a flag saying which edge the vertex belongs to. 130 vertices, 128 triangles, about a kilobyte, shared by every band in the document.

src/bandSurface.ts · the entire geometry 
function buildLadder(rungs: number): InstancedBufferGeometry {
    const params = new Float32Array((rungs + 1) * 4)
    const indices: number[] = []

    for (let i = 0; i <= rungs; i += 1) {
        const t = i / rungs
        const o = i * 4

        params[o]     = t;  params[o + 1] = 0   // upper edge
        params[o + 2] = t;  params[o + 3] = 1   // lower edge

        if (i < rungs) {
            const upper = i * 2
            indices.push(upper, upper + 1, upper + 2, upper + 2, upper + 1, upper + 3)
        }
    }

    const geometry = new InstancedBufferGeometry()

    geometry.setAttribute('aParam', new BufferAttribute(params, 2))
    geometry.setIndex(indices)

    return geometry
}

The vertex shader turns (t, side) plus the instance's six floats into a world position. Because the placement happens per vertex per frame, zooming touches no geometry whatsoever — the CPU does not retessellate, does not re-upload, and does not know that the zoom changed except to hand the shader a different matrix.

Why 64. Measured, not guessed: worst-case chord error 0.41 px in x and 0.06 px in y at 200× zoom on the widest band in 5520+. A sweep of 16/32/64/128 showed flat frame time — rung count is free in this range — and the pixel differences across the sweep were indistinguishable from camera reproducibility across page loads. The spike swept it from the URL; it is a constant now.

src/bandSurface.ts · the vertex shader, in full 
in vec2 aParam;     // x: curve parameter 0..1, y: 0 = upper edge, 1 = lower edge
in vec4 iSpan;      // x0, y0, width, y1 — y0/y1 are the upper edge, world space
in vec2 iControl;   // control abscissa of the upper and lower edge, as a fraction
in float iStrandId; // the haplotype this band belongs to

void main() {
    float t = aParam.x;
    float side = aParam.y;

    // Each edge carries its own control abscissa; they differ, so a band's thickness
    // varies along its length and the two edges are not translates of each other.
    float u = mix(iControl.x, iControl.y, side);

    float x = iSpan.x + iSpan.z * (3.0 * u * t * (1.0 - t) + t * t * t);
    float y = mix(iSpan.y, iSpan.w, t * t * (3.0 - 2.0 * t)) - side * uThickness;

    // Grow the band by a pixel on each side so a band thinner than one pixel still
    // covers a fragment to compute coverage in.
    y += (1.0 - 2.0 * side) * uPad;

    // Exact texels by integer id — no filtering, so no chance of two haplotypes'
    // appearance being blended into a third that belongs to neither.
    int id = int(iStrandId + 0.5);
    int row = int(uAppearanceRow);
    vec4 appearance = texelFetch(uAppearance, ivec2(id - (id / row) * row, id / row), 0);

    vColor = appearance.rgb;
    vEmphasis = appearance.a;

    vSpan = iSpan; vControl = iControl; vStrandId = iStrandId;
    vT = t; vWorld = vec2(x, y);

    gl_Position = projectionMatrix * modelViewMatrix * vec4(x, y, 0.0, 1.0);
}

Two bold lines are the entire geometry of the tube map. Everything else in the shader is bookkeeping: fetch the appearance, hand the fragment shader what it needs to redo this arithmetic at its own pixel.

03

Coverage, solved rather than sampled

At fit-to-width, 464 strands land on about 177 device rows: 2.6 haplotypes share every pixel row, and a band is 0.19 CSS pixels tall. This is the regime the whole antialiasing question lives in, and it is where hardware multisampling stops being an approximation and starts being a lottery.

Four-sample MSAA does not blur 2.6 overlapping sub-pixel bands into a mixture. Each of the four sample points is won outright by exactly one band. At most four of the bands covering a pixel can be represented at all; the rest are simply discarded. The result looks crisp and saturated and is missing data.

So the fragment shader computes coverage itself. Each fragment knows its own world x. It inverts x(t) for each edge — Newton, two steps, from a starting guess the rasterizer already interpolated for it — evaluates both edges there, and intersects the resulting vertical span with its own pixel box.

src/bandSurface.ts · COVERAGE — shared verbatim by both passes 
/**
 * Recover the curve parameter at this fragment's own x. The rungs give a value that is
 * close — it is linearly interpolated between two points on a curve — and two Newton
 * steps from there are exact to well inside a pixel.
 *
 * f(t)  = 3u·t·(1-t) + t³ - p
 * f'(t) = 3u·(1-2t) + 3t²,  which bottoms out at 3u(1-u) > 0, so this cannot stall.
 */
float parameterAt(float p, float u, float t) {
    for (int i = 0; i < 2; i += 1) {
        float f = 3.0 * u * t * (1.0 - t) + t * t * t - p;
        float d = 3.0 * u * (1.0 - 2.0 * t) + 3.0 * t * t;

        t -= f / max(d, 1e-5);
    }

    return clamp(t, 0.0, 1.0);
}

float bandCoverage() {
    float p = clamp((vWorld.x - vSpan.x) / vSpan.z, 0.0, 1.0);

    // Each edge has its own control abscissa, so each needs its own parameter at this x.
    float tTop = parameterAt(p, vControl.x, vT);
    float tBot = parameterAt(p, vControl.y, vT);

    float yTop = mix(vSpan.y, vSpan.w, tTop * tTop * (3.0 - 2.0 * tTop));
    float yBot = mix(vSpan.y, vSpan.w, tBot * tBot * (3.0 - 2.0 * tBot)) - uThickness;

    float lo = max(yBot, vWorld.y - uHalfPixel);
    float hi = min(yTop, vWorld.y + uHalfPixel);

    return clamp((hi - lo) / (2.0 * uHalfPixel), 0.0, 1.0);
}

Two Newton iterations, unrolled, no branches, no early exit — the derivative is bounded below by 3u(1−u) over the measured range u ∈ [0.30, 0.70], so convergence is guaranteed and the loop can be a fixed two steps rather than a convergence test. The starting guess is free: it is the interpolated vT, which the rasterizer computed anyway.

The Newton step is the piece a graphics reader should linger on. Analytic coverage for a curved shape normally means either a distance field (which needs a precomputed texture and gets the closed-form wrong near high curvature) or a per-pixel root-find with an unknown starting point. Here the mesh has already told each fragment roughly which t it is at, because that is what the rasterizer does with a varying. The ladder is not merely a tessellation; it is a distributed initial guess.

What it buys, measured

Both arms were built in the spike, sharing geometry and one shader behind a define, swapped live with the space bar so the two could be judged on the same frame. Measured at fit on 5520+, over a 600×155 device-pixel window well inside the map:

 Table 2. Analytic carries ~10× more distinct colour and 18% more distinct values per column — the banding structure the renderer exists to preserve.

And it is visibly washed toward white, which is arithmetic rather than a bug. Bands abut exactly; compositing 2.6 independently-covered opaque bands into one pixel leaves 1 − (1−0.38)^2.6 ≈ 30% of the background showing through. That is the classic conflation artifact — SVG has exactly the same defect, so the analytic arm is faithful to the document, and faithful is not automatically prettier.

The artifact is not confined to sub-pixel zooms, either. It lives at every band boundary at every zoom, because a boundary pixel is always split between two abutting bands, and strands are stacked at a regular pitch so every seam is in phase:

The correct fix, and why it is not built

Because bands abut and are opaque, the right answer at sub-pixel scale is a coverage-weighted average of the covering bands with no background term — normalise by total coverage instead of compositing over white. That gives full saturation and exact proportions: better than SVG rather than equal to it. It costs order-independence, and where two strands genuinely cross, the painter's-algorithm z-order that instance order currently carries would be lost. Front-most-wins was deliberately kept when picking was designed. Filed as its own ticket rather than folded into a rendering tidy-up.

A third technique, never built. Evaluating the curve entirely in the fragment shader over a bounding quad gives analytic coverage with no mesh at all — but a strand that jumps most of the map's height does so over a narrow horizontal span, so its bounding box is enormous and the band inside is a sliver: 8.07× overdraw. It remains the answer if the ladder ever facets at high zoom, and it is now known to be affordable — 8.07× on 2.5 megapixels is ~20 megapixels of fill, unremarkable on this hardware.

04

The pad: a floor, not a size

A band 0.19 CSS pixels tall has a real problem before coverage is ever computed. If nothing intervenes, the rasterized quad may not contain any sample point, in which case the fragment shader never runs and the band contributes nothing — not a faint line, nothing. Its colour is the information, and a band that isn't drawn is a haplotype that isn't there.

So the vertex shader grows every band by one device pixel on each side, and the fragment shader then reports its true coverage over that pixel. The geometry is inflated; the ink is not.

The rule this follows

A feature's size is corrected only where scale destroys information the feature carries. Everything else is drawn at the scale the camera says, and the server's numbers survive the trip unmodified. uPad qualifies because a band that falls between sample rows loses its colour entirely — and it is a floor: above one pixel it does nothing, and thickness 15 scales freely from 0.19 CSS px at fit to 38 at 200×.

A segment box's 2-unit stroke was going to be pinned at 2 CSS px on similar reasoning. The number behind that was simply wrong — a scaling stroke spans 0.016 px at fit to 3.1 px at 200×, so there was never anything to fix. It scales, like everything else.

05

Appearance as a table, not an attribute

The obvious place for a band's colour is a per-instance attribute. That is what the spike shipped, and it is what makes interactive highlighting impossible.

A strand is drawn as dozens of separate bands — 13 to 47 across the surveyed documents, 87 on 5520+ — scattered through document order. With colour as an attribute, changing how one haplotype looks means finding and rewriting its share of a 162 KB buffer and re-uploading it — per pointer move. Moving the data one level of indirection away fixes this completely: one texel per strand, RGB plus an emphasis byte, fetched in the vertex shader by iStrandId.

Holding Shift turns the cursor into a feeler: the strand it touches is drawn in full, everything else recedes to 8% alpha, and releasing brings the whole map back. On the SVG surface this same interaction was built and shipped switched off, because invoking it cost ~28 ms of style invalidation per swap. Here:

Highlighting is not what the frame costs.
src/bandSurface.ts · the fragment shader, in full 
void main() {
    float coverage = bandCoverage();

    if (0.0 >= coverage) {
        discard;
    }

    // One multiply, and only ever downward: the focused strand and a map with no key
    // held are both emphasis 1 and are drawn identically.
    fragColor = vec4(vColor, coverage * vEmphasis);
}

Emphasis reaches alpha and never vColor. PCLAI colour is shared vocabulary with two other panels a researcher reads alongside this one, so the renderer may dim a strand but may never recolour it. Receding therefore turns a strand into a ghost of itself — whatever is behind it shows through, including the focused strand crossing over it — rather than repainting it grey, which would collide with grey's existing meaning (pclaiX="None").

A reversal worth recording. The ticket, the spec and the decision log all asked for touched strands to accumulate into a comparison set. Built that way, looked at, and reversed on the evidence: swept across a bundle, accumulation leaves a widening trail of lit strands and the one strand being pointed at ends up as one of dozens at full colour — the opposite of telling it apart. The table is indifferent: it holds a byte per strand and has no opinion about how many are lit, so a deliberate comparison-set gesture needs no change here.

Why 256 wide. MAX_TEXTURE_SIZE is only guaranteed to be 2048 in WebGL2 and the parser admits strand ids to 65535, so a one-row table is a table that works until it doesn't. 256 per row puts the whole admissible range inside 256 rows.

06

Picking: the same shader, asked a different question

“Which haplotype is under the cursor” is the capability the SVG surface lost — DOM hit-testing at 40,442 elements cost ~28 ms per hover. The GPU already knows how to rasterize these bands. So the renderer asks it what it put there.

A second pass runs over the same scene with a material that is the band material's twin: same vertex shader, same coverage test, differing only in what it writes. The camera's entire frustum is the one CSS pixel under the cursor; the target is 1×1; the pixel is read back synchronously.

src/bandSurface.ts · PICK_FRAGMENT 
precision highp float;
${COVERAGE}          // ← the identical string the visible pass compiles

flat in float vStrandId;

out vec4 fragColor;

void main() {
    if (0.0 >= bandCoverage()) {
        discard;
    }

    float low = mod(vStrandId, 256.0);
    float high = floor(vStrandId / 256.0);

    fragColor = vec4(low / 255.0, high / 255.0, 0.0, 1.0);
}
Why the coverage test is shared as a string

Sharing it is a correctness property, not a tidiness one. Picking answers “which band put ink in this pixel”, and the only way that answer cannot drift from what the screen shows is for both passes to run the same test over the same varyings from the same vertex shader. Two copies of this arithmetic would be two opinions about where a band is — and they would disagree exactly at the sub-pixel edges where it matters most.

Four smaller decisions in this pass are each worth one sentence:

  • Alpha is a hit flag, not a colour. Every kept fragment writes 1 and the target clears to 0, so “nothing here” is distinguishable from strand 0 — a real haplotype on every document we have.
  • Blending is off and there is no depth buffer, so the last fragment written wins; instances are drawn in document order, so that is the topmost band — the same answer SVG's own hit-testing gave, and the one the researcher is looking at where strands cross. Blending two ids would produce a third naming a strand neither band belongs to.
  • Emphasis is deliberately not applied here. A receded strand is exactly what the feeler is reaching for next; a pick pass that dimmed along with the picture would make the strands a sweep has not yet touched progressively harder to touch.
  • Picks are coalesced to one per frame. Pointer devices report well above 60 Hz and every pick is a synchronous readback that stalls the pipeline — answering each event would stall several times for one frame of movement, and only the last answer is ever read.

Honest numbers. readRenderTargetPixels blocks until the pass finishes, so the milliseconds reported with each pick include the GPU work rather than just the time to submit it. The pick is the largest single item in the 9.4 ms sweep frame — and the frame is still inside budget.

07

The same shader at 1/150 scale

The navigator thumbnail renders this scene into a render target 720 px wide — one camera change, once per document — and reads it back. Same scene, same shader, same instance buffer; only the camera differs. The alternative was to serialize a second copy of the document and let the browser rasterize it, which is two pictures from two pipelines with nothing keeping them the same.

This puts the coverage path at the far end of the regime Table 3 measures. A device pixel is ~300 world units and a band is 15, so ~20 strands share every pixel row instead of 2.6. Both consequences are the arithmetic behaving as designed: uPad is doing real work, because without it a 0.05 px band falls between sample rows and the thumbnail becomes a picture of whichever strands happened to land on one; and the wash toward white is stronger still, because twenty independently-composited 0.05-coverage bands leave most of the background showing. The thumbnail is pale, and it is pale in proportion to what is there, which is what a thumbnail is for.

The unbuilt normalisation would help here more than anywhere — 20 bands averaged by coverage with no background term is a saturated, proportionally correct thumbnail.

The structural reason is worth stating plainly, because the frame time alone understates it. The SVG surface also panned at 8.3 ms — but only by handing the compositor a new matrix for a bitmap it already had, which is exactly why zoom re-rasterized a 900-megapixel layer and came apart. Here the canvas is 2.5 megapixels at every zoom level and geometry is never rebuilt, so the failure is structurally absent rather than avoided.

Per frame, the CPU does: one uniform write for the device-pixel size, one drawElementsInstanced, one CSS transform on the segment-box overlay, and two style writes on the navigator rect. Nothing is proportional to the band count. 09

What would break it

This design buys its performance by knowing the shape of its input exactly. That is a real constraint and it should be stated as one, not discovered later.

If this changedConsequence
A band that isn't the canonical shapeThe parser recognises one grammar and rejects the whole document, loudly. Partial rendering is never offered: a half-drawn map looks like a correct map of different data.
A control abscissa outside the spanx(t) stops being monotone, a pixel's x maps to two points on the curve, and the Newton inversion is answering an ill-posed question. Measured at u ∈ [0.30, 0.70] across every document, so there is real margin — but it is margin, not a guarantee.
Text in the documentThere is none in any of the 17 documents surveyed. It would need a genuinely different answer, not an extension of this one.
A thickness other than 15Harmless. It becomes a seventh float.
More than 65,535 strandsThe pick pass encodes the id in two bytes and the instance buffer is Uint16. The parser refuses a document that would wrap it, rather than returning a wrong answer quietly.
Bands that genuinely overlap rather than abutOrder-independent coverage normalisation — the unbuilt improvement in §03 — would become wrong rather than merely lossy. Instance order carrying z-order is the assumption doing the work.
The transferable part

Very little here is about genomics. The reusable shape is: survey the real input until a closed-form parameterisation falls out; store the parameters, not the geometry; give the fragment shader enough of the parameterisation to re-derive the exact answer at its own pixel; and move anything that changes interactively into a lookup indexed by identity rather than into the geometry stream. Each of those steps replaces a cost proportional to the number of drawn things with a cost proportional to nothing at all.
